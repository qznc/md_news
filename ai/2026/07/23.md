# MCP Workflows Bring Structure and Precision to LLM-Assisted Development

The Model Control Protocol (MCP) is emerging as a practical layer between large language models and the tools they invoke. Instead of letting an agent wander through a codebase or a research task unguided, MCP servers expose focused capabilities—symbol-level code navigation, gated research-to-implementation pipelines, and persistent workflow state—that the model can call when the user explicitly opts in. Two open-source examples, [SymbolPeek](https://github.com/pioner92/symbolpeek-mcp) and [deep_learning_auto_research](https://github.com/fikayoAy/deep-learning-auto-research), show how this pattern reduces token waste, enforces review checkpoints, and keeps the human in control.

## SymbolPeek: Surgical Code Navigation

SymbolPeek is an MCP server that lets an agent request a single symbol—function, class, hook, JSON property, Markdown heading—rather than reading an entire file. The server uses the TypeScript Compiler API for semantic analysis of TypeScript and JavaScript, and Tree-sitter for syntax-level parsing of Rust, Python, Java, Go, JSON, and Markdown. A request for `createProject.collectImports` in a 1,791-line worker file returns 39 lines (2 KB) instead of the full 65 KB. The response includes source ranges, inferred types, and trust metadata such as `analysis_level: "syntax"` or `"semantic"` and `complete: true/false`.

Tools fall into four groups: navigation (`read_symbol`, `list_symbols`, `search_symbols`, `go_to_definition`, `read_symbol_context`), code intelligence (`find_references`, `find_callers`, `find_callees`, `find_dependencies`, `get_call_hierarchy`), type analysis (`get_type`, `find_implementations`, `get_document_outline`, `get_diagnostics`), and discovery (`get_capabilities`, `get_statistics`). Cross-file resolution honors `tsconfig.json` path aliases and barrel re-exports, which plain `grep` cannot reliably follow. For unsupported languages or operations the server returns an explicit error rather than empty results, so the agent knows the limitation immediately.

Installation is a one-line script that verifies a checksum, places a binary in `~/.local/share/symbolpeek` (or `%LOCALAPPDATA%\SymbolPeek` on Windows), links `symbolpeek` and `sym` into `PATH`, and prints the exact `codex mcp add` or `claude mcp add` command. An optional skill file nudges the model to reach for these tools before opening whole files. The server parses files on demand; there is no index to rebuild and no stale cache.

Where SymbolPeek shines: extracting one symbol from a large file, impact analysis across aliases and re-exports, resolved generic types (`useAsync<FeedPermission, Error>`), and scoped discovery (e.g., “hooks matching `conversation`”). Where it does not: plain text, comments, small config files, unsupported extensions, full control-flow reading inside one function, and very large TypeScript monorepos where program construction latency makes a targeted `grep` faster for a single lookup.

## deep_learning_auto_research: Gated Research-to-Code Pipeline

The second project applies the same opt-in philosophy to deep-learning implementation. An engineer writes a markdown system plan describing goals, components, and intended direction. The MCP server then guides Codex through a fixed sequence:

1. Decompose the plan into semantic implementation blocks (not generic phases).
2. Attach research papers to each block.
3. Extract only block-specific evidence from those papers.
4. Create a `spec.md` from the block, papers, and extracted research.
5. Approve the spec.
6. Prepare a strict implementation context that gates coding behind the approved spec.
7. Implement the block in dependency order.
8. Record and verify the implementation.
9. Synthesize final context after all blocks are done.

Artifacts live under `<PROJECT_PATH>/.planner/` (`state.json`, `graph.json`, `audit-log.jsonl`, per-block `block.md`, `papers.md`, `extracted-research.md`, `spec.md`, `implementation.md`). Every transition—block proposal, research approval, spec approval, implementation recording, verification—requires an explicit human reviewer name. The implementation target (language + framework) must be set before spec generation so the model cannot guess from the MCP repo itself.

Prompt templates cover project setup, target setting, research (online search or user-provided PDFs), spec creation, implementation, verification, and final synthesis. Rules forbid automatic advancement: Codex must wait for the user to say “Use deep_learning_auto_research. <action>” at each stage. A `reimplement` mode allows redoing a block without bypassing gates.

## Pros of the MCP Approach

- **Token efficiency.** SymbolPeek’s 2 KB vs. 65 KB example is typical; the deep-learning workflow avoids dumping whole papers into context by extracting only block-relevant passages.
- **Auditability.** Every artifact is a markdown file; `audit-log.jsonl` records who approved what and when.
- **Human control.** Opt-in invocation, mandatory approvals, and explicit `reimplement` mode prevent silent scope creep.
- **Language breadth.** SymbolPeek supports six language families with appropriate backends; the research workflow is language-agnostic.
- **No stale state.** On-demand parsing and per-block markdown files eliminate index drift.
- **Composability.** Any stdio MCP client (Codex, Claude Code, custom) can connect; the protocol is the contract.

## Cons and Friction Points

- **Setup overhead.** Node.js 20+, MCP client configuration, and (for TypeScript) a valid `tsconfig.json` are prerequisites.
- **Syntax-only for non-TS languages.** Rust, Python, Java, Go, JSON, and Markdown use Tree-sitter without cross-file semantic resolution; `find_references`, `go_to_definition`, `get_type`, and call hierarchy are unavailable.
- **Latency on large TS codebases.** Building the TypeScript program for a monorepo can take seconds; a quick `grep` may win for one-off lookups.
- **Windows path quoting.** Spaces in paths require careful escaping in the MCP config and prompt templates.
- **Learning curve.** Engineers must internalize the staged workflow and prompt vocabulary; deviation returns “block not ready” errors.
- **Not a universal replacement.** Small files, comments, config, and unsupported extensions still need traditional tools.

## Conclusion

MCP does not automate the engineer away. It automates the busywork—file reads, grep loops, context assembly—while inserting mandatory checkpoints that keep the human as the decision authority. SymbolPeek proves the token savings are real and the tooling is production-ready. deep_learning_auto_research shows the same pattern scales to multi-stage research and implementation pipelines. The trade-off is upfront configuration and discipline: you must invoke the workflow explicitly, approve each gate, and maintain the environment. Teams that accept that discipline gain traceable, reviewable, and token-efficient LLM assistance; teams that want zero-config magic will find MCP too heavy.
