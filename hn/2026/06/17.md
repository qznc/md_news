# Local LLMs Are Useful Now, but the Hardware Tax Is Real

A recent field report on [Vicki Boykis’s 2026 local model field report](https://vickiboykis.com/2026/06/15/running-local-models-is-good-now/) is interesting because it shows that locally run models have moved from novelty to practical developer aid, while community reactions and benchmark data show that the remaining friction is mostly hardware, setup, reliability, and expectations.

## The state of local models

Local models are no longer only a demo for people who enjoy compiling C++ at midnight.

Boykis reports that a 2022 M2 Mac with 64 GB of RAM and 1 TB of storage can run models such as Mistral 7B, Gemma 3, OpenAI OSS-20B, Qwen 3 MoE, and Qwen Coder variants through tools such as llama.cpp, Open WebUI, llama-cpp-python, Ollama, llamafiles, and LM Studio.

The bigger shift is not just that the models can start, but that they can sometimes answer development questions without first checking an API model.

Her rough test was whether she had to double-check local output against a frontier model, and she says she started doing that less often after OpenAI OSS-20B.

Here, frontier means the strongest cloud models from large AI providers.

With Gemma 4, she says local agentic coding can reach about 75 percent of the accuracy and speed of frontier models for some loops.

That is a major change from six months earlier, when the same kind of local workflow would often feel impossible.

## Where they are useful

Local models are best treated as fast, private assistants for bounded tasks.

Boykis uses them for development questions that do not require fresh information, refactoring notebooks into modules, linting type hints, proofreading posts, writing unit tests, and bootstrapping small repositories.

The most realistic pattern is not “replace the best cloud model with one local model.”

The more realistic pattern is “ask the local model for a first pass, review it, and use a stronger model only when the task is large or ambiguous.”

Several users make the same point in the [Hacker News discussion of local model usability](https://news.ycombinator.com/item?id=48555993), where local models are praised for smaller tasks but criticized for broad coding-agent work.

A hybrid approach is also practical, with local models handling small, private, repetitive work and cloud or hosted open-weight models handling larger planning tasks.

## What still hurts

The main constraint is hardware.

Dense models use all their parameters for each token, so they can be smarter but slower.

Mixture of Experts models, often shortened to MoE, use only part of the model for each token, so they can be faster but may make more mistakes.

Quantization reduces model size by storing weights with fewer bits, but low-bit quantization can weaken reasoning and tool calling.

One commenter warns that 4-bit quantization can feel like lobotomizing a model, and suggests higher-bit quantizations such as 5-bit for dense models and 6-bit for MoE models.

The practical result is that local LLMs need memory, memory bandwidth, and fast storage, not just a modern laptop.

Prefill, which is processing the prompt, needs compute.

Decode, which is generating the answer, needs bandwidth.

The KV cache, which stores attention state during a conversation, can grow until it consumes a large share of system RAM.

Boykis notes that her KV cache can grow to 64 GB of RAM during work.

Several commenters also report that laptops can become loud, hot, and uncomfortable during sustained local inference.

## Setup and reliability

Running an agent locally requires three pieces.

An inference engine runs the model.

A model artifact is the downloaded set of weights.

An agent harness gives the model tools and a workflow.

Boykis uses Pi as the harness and LM Studio as the inference server, then runs sessions in Docker with limited permissions.

That sandboxing matters because an agent can edit files, run commands, or browse the web if the setup allows it.

The ecosystem is easier than it used to be, with tools such as LM Studio, Ollama, and Hugging Face’s “Use This Model” button, but it is still not frictionless.

Prompt template mismatches, model configuration, context-window tuning, and harness quirks can still break a session.

Direct llama.cpp may be faster than a graphical or API wrapper in some cases, but easier tools can be worth the overhead for many users.

## Privacy and control

Local models appeal to people who do not want to send code, documents, or personal notes to a third-party service.

They also appeal to people who want stable behavior, predictable cost, and the ability to inspect what is happening.

Boykis emphasizes that local systems let users watch token generation, change context windows, compare quantizations, and pit models against each other.

That level of control is one of the strongest reasons to run locally.

The broader control issue is not limited to AI, as shown in a [GrapheneOS discussion about Volkswagen app compatibility](https://discuss.grapheneos.org/d/35949-volkswagen-app?page=3), where users discussed telemetry, remote-control risks in connected cars, and app breakage around integrity checks and unsupported operating systems.

Local AI can reduce dependence on cloud providers, but it does not remove the need to secure the machine, sandbox tools, and review outputs.

## Benchmarks and expectations

Open-weight models are improving quickly, but benchmark numbers do not automatically translate into smooth local use.

The [Artificial Analysis profile for GLM-5.2](https://artificialanalysis.ai/models/glm-5-2) describes it as a 753-billion-parameter reasoning model with 40 billion active parameters per token, a 1-million-token context window, 110.7 output tokens per second, and API pricing of $1.40 per million input tokens and $4.40 per million output tokens.

It also scores 51 on the Artificial Analysis Intelligence Index and is described as fast but expensive compared with similar open-weight models.

Those figures show the ceiling that local setups are chasing, not a baseline that every laptop can reach.

Local models are most convincing when the task is narrow, the prompt is specific, and the user is willing to review the result.

They are least convincing when the task requires long-horizon coding, broad world knowledge, fresh information, or reliable tool calls with little supervision.

## Practical guidance

Start with a smaller model if you only have a laptop.

Use a larger model when the task needs more reasoning and you can tolerate slower output.

Keep the agent in a sandbox before giving it file or shell access.

Prefer smaller tasks over giant instructions.

Use a cloud or stronger hosted model to create a plan if the local model keeps getting stuck.

Expect to tune quantization, context length, system prompts, and tool permissions.

Treat local models as a controllable workshop, not a self-driving car.

## Bottom line

Local LLMs are good enough to be useful now, but not easy enough to be invisible.

They can save money, protect private data, and make repetitive developer work faster.

They still demand expensive hardware, careful setup, and realistic expectations.

For many users, the best near-term answer is hybrid: local models for cheap, private, repeatable work, and stronger hosted models for ambiguous, high-stakes, or long-running work.
